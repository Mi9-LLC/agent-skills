# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository purpose

This is the **Mi9 LLC public catalog of Claude Code Agent Skills**, hosted on GitHub at `github.com/Mi9-LLC/agent-skills`. Teammates and external users install individual skills with:

```
npx skills add https://github.com/Mi9-LLC/agent-skills --skill <skill-name>
```

It is **not** application code. There is no build, test, or lint pipeline — the entire repo is Markdown skill definitions. Do not invent commands; there are none to run.

## Layout

Flat skills layout, matching the canonical [`anthropics/skills`](https://github.com/anthropics/skills) example:

- `skills/<name>/SKILL.md` — the **skill definition** (YAML frontmatter with `name`, `description`, `allowed-tools` + Markdown body that's loaded into the model when the skill triggers).
- `skills/<name>/references/` — on-demand reference docs the skill reads itself when it needs the detail. Keep these out of `SKILL.md` so the always-loaded body stays small.

`.claude-plugin/marketplace.json` and `hooks/` are the one exception to the flat layout. They exist because `npx skills add` installs skill files only: `clear-and-short` needs a `UserPromptSubmit` hook, and `execute-change` needs three subagent-watching hooks plus a process-sweep script. Read "Distribution mechanism" below before adding a third plugin.

The one other top-level directory is `evals/` — skill eval fixtures (e.g. `evals/session-handoff/`) kept out of the installable skill folders. It is development material only: `npx skills add` installs a single `skills/<name>/` tree and never pulls `evals/`, so nothing here ships to consumers.

- **`convert-plan-to-feature`** (`skills/convert-plan-to-feature/`) — Decomposes an approved plan into independently-trackable, per-feature implementation specs under a dedicated `<plan-location>/<initiative>/` subfolder (the repository's own plan location checked first — its CLAUDE.md and existing folders, e.g. `docs/up next/` — defaulting to `docs/plans/`): a `REQUIREMENTS.md` index (context, blast radius, cross-cutting catalogs, deploy ordering, parallel groups, feature table with a Status column — the initiative's status board; when every feature is done the folder follows the repo's docs contract, many repos pruning implemented plans) plus one `features/NN - <name>.md` file per unit of work, each with its own requirements, technical steps with real file paths, dependencies, acceptance criteria, and a verbatim *Standing instructions for the implementer* block (open questions go back to the requester, never resolved by assumption; external library/API behavior verified against current docs, not internal knowledge; the file's acceptance criteria are the verification contract `verify-implementation` runs against, so a mid-feature scope change is written back into them). A feature that modifies existing behavior must carry an acceptance criterion naming its regression test. Model assignments are **quality-first**: Opus is the default; Sonnet/Haiku only when a feature meets every condition of the cheaper tier; any underestimation signal (shared contracts, cross-component work, concurrency/caching/migrations/auth, modified existing behavior, open questions, "just/simple/quick" wording) forces Opus; a mandatory second pass re-reviews every assignment after all files are written (in doubt between tiers ⇒ the higher one), and the plan's own per-phase recommendations are input, not authority. Parallel groups mark concurrency mechanically (no dependencies ⇒ group 1; otherwise 1 + highest dependency group; same group ⇒ no mutual dependencies ⇒ safe to implement concurrently), recorded in the features table and each file's header and consistency-checked at the verify step — so a step-5 fleet coordinator never re-derives the dependency graph. On a re-run where the `<initiative>/` folder already exists it reads the existing `REQUIREMENTS.md` first, preserves every feature's Status value, and asks (AskUserQuestion) before overwriting any feature file whose status is past `todo`. **Produces planning documents only — does not implement anything.** Declares `disallowed-tools: Edit, NotebookEdit` to drop those tools while the skill is active (a per-turn guard — clears on the next message). Invoke when a finished/approved plan exists (from plan mode or under `docs/plans/`) and the user wants it split into trackable features/tickets/specs — but NOT in a repository that mandates its own spec workflow (e.g. OpenSpec repos, where the change's `tasks.md` owns the breakdown; there the skill's execution rigor — model rubric, parallel groups, acceptance criteria, standing implementer instructions — is ported into that artifact instead of a parallel breakdown).

- **`systematic-debugging`** (`skills/systematic-debugging/`) — Root-cause-first debugging discipline adapted from `obra/superpowers` (MIT, © 2025 Jesse Vincent). Four phases: root-cause investigation → pattern/context analysis → ranked hypotheses, one tested at a time → fix the cause behind a failing test. **Iron law: no fix without root-cause investigation first; after 3 failed fixes, stop and question the architecture rather than trying a 4th.** States the running fix-attempt count in the visible reply on every failed fix. Phase 1 requires a reproduction loop before any diagnosis — one named command, run once with its output shown, that fails on the exact symptom, fast and deterministic (or, for a flaky bug, at the highest reproduction rate reachable — `condition-based-waiting.md` has the loop/parallel/load/injected-sleep techniques), then minimised one element at a time; temporary logs carry a unique `[DEBUG-xxxx]` prefix so cleanup is one grep. Phase 3 lists 2–4 ranked hypotheses, each with a falsifiable prediction, and tests only the top one; a failed test moves to the next on the list, re-ranked. Phase 4's regression test goes at a seam that exercises the bug as it happens at the real call site (no correct seam ⇒ a finding). `root-cause-tracing.md` adds a redaction rule for shown diagnostics (`<REDACTED>`, credentials only via environment variables). Decoupled from the superpowers hook/dispatcher/sibling skills; **Windows-clean** (no unix-only shell to run); examples for **.NET/xUnit + TS/Vitest**. Ships `references/` (root-cause-tracing, defense-in-depth, condition-based-waiting). `allowed-tools: Read, Grep, Glob, Bash, Edit, Write`. The reproduction-loop, ranked-hypotheses, seam, log-tag, redaction, and flaky-rate rules are adapted from `mattpocock/skills` `diagnosing-bugs` (MIT, © 2026 Matt Pocock).
- **`test-driven-development`** (`skills/test-driven-development/`) — **Opt-in** red-green-refactor discipline adapted from `obra/superpowers` (MIT, © 2025 Jesse Vincent). Write a failing test → watch it fail for the right reason → minimal code to pass → refactor; with a rationalization-rebuttal table and anti-pattern guidance. **Deliberately narrow trigger:** fires only on an explicit TDD ask or a new feature the user wants built test-driven — never on every edit, routine bug fix, or trivial change. Before the first test it lists the test seams (the public boundaries the tests go through — existing ones preferred, fewer is better) and confirms them with the user via AskUserQuestion, or states them in the report when running non-interactively; expected values come from an independent source (a literal, a worked example, the spec), never recomputed the way the code computes them; horizontal slicing (all tests first, then all code) is named as a rationalization — one test, then one implementation. `testing-anti-patterns.md` adds the mocking-boundary rule (mock at the lowest boundary that owns the slow or external effect; having to mock one of your own modules is a design smell to report) and Anti-pattern 6, verifying through a side channel (asserting via a DB query or internal state instead of the interface). Decoupled from the superpowers hook/dispatcher; examples for **.NET/xUnit + TS/Vitest** with Windows-friendly commands. Ships `references/testing-anti-patterns.md`. `allowed-tools: Read, Write, Edit, Bash, Grep, Glob, AskUserQuestion`. The seam, independent-expected-value, horizontal-slicing, mocking-boundary, and side-channel rules are adapted from `mattpocock/skills` `tdd` (MIT, © 2026 Matt Pocock).

- **`retro`** (`skills/retro/`) — Git-log engineering retrospective for the current repo. A bundled zero-dependency Node script (`scripts/git-retro.mjs`, Node >= 18) computes every metric deterministically (commits, contributors, LOC, test ratio, per-author 45-minute-gap work sessions, hourly histogram, commit-type mix, churn hotspots, approximate PR count/size buckets, focus score, ship-of-the-window, streaks, AI-assisted-commit share via `Co-Authored-By` trailers) and emits JSON; the model only writes the narrative on top of it and may never state a number absent from that JSON. A retro/retrospective/trend ask gets the full 11-section 1,500–2,500-word narrative; a narrower stat-shaped ask gets a short form instead (one-liner + summary table + only the sections it asked about). Flags: `--window 7d|24h|Nd|Nh|Nw` (default 7-day window), `--compare` (prior same-length window computed live from git, plus deltas), `--base <ref>`, `--no-fetch`. Honesty guards in the JSON (`zeroCommits`, `staleBase`, `fetchFailed`, `noRemote`, `detachedHead`, `shallowClone`) must be carried into the narrative verbatim — a zero-commit window is reported as exactly that, never padded. Terminal-only by default; `--save` writes a JSON snapshot to `docs/retros/` and the model then writes `docs/retros/<YYYY-MM-DD>-retro.md`. **Never commits or pushes.** Per-author output is stats-only (leaderboard + a personal deep-dive for the runner) with no individual praise/critique — improvement suggestions are team-level only, and it refuses performance-review/HR asks. `allowed-tools: Bash, Read, Write`; `disallowed-tools: Edit, NotebookEdit`. Adapted from `garrytan/gstack` (MIT, © 2026 Garry Tan); gstack-state integrations (learnings, Greptile, telemetry, global mode) dropped.
- **`verify-frontend-change`** (`skills/verify-frontend-change/`) — Browser-verification loop that forbids calling a frontend/UI change done from a successful edit, green build, or HMR reload alone. Five steps driven through the **Chrome DevTools MCP server** (required; if absent the skill stops and reports the change *unverified*): start/reuse the dev server (background task; URL taken from the server's own output, never assumed) → open the affected route → interact with the changed behavior itself → console gate (zero new errors; unattributable errors count as new, pre-existing ones reported, never silent) → performance trace (fails on change-attributable regressions; dev-mode-numbers caveat). **Any failure → fix → rerun from Step 1**, never resume mid-loop; after 3 failed fix cycles on the same step, stop and question the approach (points to `systematic-debugging`). Exactly two end states: Verified-with-evidence or Blocked/unverified — no "probably fine". Stops only dev servers it started. Declares no `allowed-tools`/`disallowed-tools` (unrestricted — the browser tools it needs are the user's own `chrome-devtools` MCP registration). Ships `references/` (`chrome-devtools-mcp.md` tool cheatsheet, `dev-server-playbook.md`).
- **`health`** (`skills/health/`) — Local quality-gate dashboard for the current repo. A bundled zero-dependency Node script (`scripts/check-health.mjs`, Node >= 18) runs the project's own gates (typecheck — JS/TS, Python, or .NET via `dotnet build --nologo` — / lint / test / dead-code / shell lint), parses their output (a clean gate's captured output trimmed to a short tail), scores each 0–10 against a weighted rubric (typecheck 25 / lint 20 / test 30 / deadcode 15 / shell 10, renormalized over whichever gates ran), and computes the weighted composite; the model only narrates that JSON and may never state or estimate a number absent from it. Config lives in `.claude/health.json`, written by the model only after the user confirms the detected stack on first run (`--detect-only` prints the proposed config; AskUserQuestion confirm; stdout written verbatim). A category whose tool isn't installed is skipped and its weight redistributes — skipped ≠ failed, never scored. Flags: `--detect-only`, `--config <path>`, `--only <cats>`, `--parallel` (opt-in concurrent gates — durations are then wall-clock-under-contention, not comparable to history), `--save [dir]` (opt-in history append to `docs/health/history.jsonl`; trend — delta, direction, per-category regressions — is read from that file automatically whenever it exists). Honesty guards carried into the dashboard verbatim: `noToolsDetected` (composite `null`, honest empty dashboard), `notGitRepo`, `dirtyWorkingTree`, `anyTimeout` (hung gate scores 0), `anyParseFallback` (exit-code-only scoring flagged as coarse), `firstRun`. Never fixes issues, never modifies the repo (writes only the `--save` history line; the model may Write a dated `docs/health/<YYYY-MM-DD>-health.md` report only on an explicit ask). **Never commits or pushes.** `allowed-tools: Bash, Write`; `disallowed-tools: Edit, NotebookEdit`. Adapted from `garrytan/gstack` (MIT, © 2026 Garry Tan); rebuilt — deterministic script replaces model-computed scoring; gbrain and `~/.gstack` state dropped; config moved to `.claude/health.json`; history opt-in and in-repo.
- **`plan-eng-review`** (`skills/plan-eng-review/`) — Pre-implementation gate that reviews a **written implementation plan** (plan-mode draft, a file under `docs/plans/`, or a pasted plan) before any code is written: scope challenge (incl. challenging any per-phase model recommendations the plan carries — quality-first, an underestimation signal forces Opus) → what-already-exists reuse check → four dimensions (architecture — including the deletion test on every planned module and the two-adapter rule (no interface/port unless two implementations are justified, normally production + test); code quality of the planned code; tests — the heaviest, including the seams-and-dependency-categories check (a planned test that must change when the implementation changes tests past the interface ⇒ a finding; fewer seams, existing ones preferred; the dependency category — in-process / locally substitutable / remote-but-owned / true external — decides the test strategy); performance) → verdict (`APPROVED` / `APPROVED WITH CHANGES` / `NEEDS REVISION`, bound by a decision table: any CRITICAL GAP or unresolved decision ⇒ NEEDS REVISION; non-empty Required plan changes ⇒ at most APPROVED WITH CHANGES). **Iron law: no finding without evidence** — presence findings quote the plan or a verified `file:line`; absence findings quote the obligation-creating plan text plus the verified negative search; findings depending on external library/framework/API behavior are verified against current documentation in-session (WebSearch/WebFetch), never internal knowledge; neither evidence form ⇒ at most a low-confidence appendix note. **REGRESSION RULE (non-negotiable): plan modifies existing behavior with no covering test → regression test enters Required plan changes, no question asked.** Max 8 findings per dimension, severity-ranked, confidence 1–10. Genuine scope/design forks go to the user via AskUserQuestion **batched per section** (never one-interrupt-per-finding); unanswered forks land under `UNRESOLVED DECISIONS:`, never silently defaulted; answered ones are recorded in a Decisions block and carried forward on re-runs, and on a re-run each prior report's Required plan changes are re-verified against the amended plan so the max-8-findings-per-dimension cap can't silently drop one. **The only mutation it ever performs** is replacing/appending the plan file's `## ENG REVIEW REPORT` section via a whole-file Write-splice (H2 boundaries matched outside fenced code blocks, trailing-`\r` tolerant; report interior `###`-only; every non-report byte preserved); no plan file on disk → terminal-only report, zero writes. Optional outside voice (one subagent prompted to refute the verdict) on explicit ask only. **Never implements the plan; never commits or pushes.** Catalog position: `new-feature` (design) → plan mode → **`plan-eng-review` (gate)** → `convert-plan-to-feature` (decomposition) → implement → `verify-implementation` (post-code gate). `allowed-tools: Read, Grep, Glob, Bash, Write, Agent, AskUserQuestion, WebSearch, WebFetch` (Bash read-only; Agent for the parallel Explore subagents in the what-already-exists reuse sweep — the reviewer re-reads every cited `file:line` itself, since a subagent report is a lead, not evidence — and for the optional outside-voice subagent; WebSearch/WebFetch only for current-docs verification); `disallowed-tools: Edit, NotebookEdit`. Ships `references/review-dimensions.md` (four checklists, coverage legend, severity/confidence tables, verdict rules, report skeleton, and the whole-file Write-splice procedure). Adapted from `/plan-eng-review` in `garrytan/gstack` (MIT, © 2026 Garry Tan); per-finding question gates → per-section batching, Codex outside-voice → optional on-request Claude subagent, test-plan/tasks artifacts folded into the single in-plan report, iron law extended to absence findings, gstack state (`~/.gstack`, `bin/` loggers, brain, TODOS.md, readiness dashboard, review chaining, Lake Score) dropped. The deletion test, two-adapter rule, and seams/dependency-categories check are adapted from `mattpocock/skills` `codebase-design` and `to-spec` (MIT, © 2026 Matt Pocock).
- **`document-generate`** (`skills/document-generate/`) — Writes human-facing documentation files — Diataxis tutorials, how-to guides, reference pages, explanations — for a named feature, module, or whole project, grounded in end-to-end codebase archaeology (implementation + tests read first) before any prose. Docs home resolves target-local convention → repo `docs/` → detected doc-framework config (Docusaurus/MkDocs/VitePress/Nextra, sidebar updated) → new root `docs/`. `allowed-tools: Read, Grep, Glob, Bash, Write, Edit, Agent` — **no `disallowed-tools`**: the skill needs Edit and Bash to do its job, so its never-rules (**never edits `CLAUDE.md`/`AGENTS.md`; never commits or pushes**) are workflow discipline rather than a tool-pool restriction, and the body says so explicitly. Ships `references/quadrant-templates.md` (four templates, per-quadrant rules, anti-mixing table, example-verification techniques, doc-framework identification table, collision-policy detail) and `references/example-and-report.md` (an annotated worked example plus the end-of-run report format). Adapted from `/document-generate` in `garrytan/gstack` (MIT, © 2026 Garry Tan); the commit/push/PR-body-update tail is dropped (this skill never commits), the `gstack-redact` binary becomes the placeholder-credentials rule, the confirm-only-above-5-docs threshold becomes the always-on partition-plan approval gate, upstream's inline-summaries-plus-standalone-files default narrows to standalone files plus minimal link lines, and the gstack machinery is dropped.
- **`stdlib-first`** (`skills/stdlib-first/`) — Behavioral reuse-before-build discipline for new TypeScript/Node and C#/.NET code: a strict 4-rung ladder (built-in/standard-library API → C#-only first-party `Microsoft.Extensions.*` → widely-adopted library the project already uses → custom implementation last) with one consistency exception (where the project already uses one library consistently for the exact task, matching that convention outranks introducing a rung-1 built-in alongside it; a genuine conflict is named to the user rather than decided silently), plus precise types (no `any`, no `object`/`dynamic`), specific error classes over bare `Error`/`Exception`, C# async with `CancellationToken` and no sync-over-async, and short doc comments on non-obvious members. **Always asks before adding a dependency (AskUserQuestion); produces no files — changes only the code Claude writes.** Description carved to the two decision moments (writing a new utility/helper/service; adding/choosing a dependency); do-NOT covers code review, debugging existing behavior, trivial edits, and other languages. Canonical copy of the `## Coding standards` block checked into Mi9 repo `CLAUDE.md` files (their `<!-- source -->` comments point here) and the bootstrap for future repos. - **`clear-and-short`** (`skills/clear-and-short/`) — Behavioral reply-compression mode: use the fewest words a reply needs in simple, correct, complete English. Compresses **which facts get stated**, never **how words are formed** — the deliberate opposite of telegraphic "caveman" compression, since dropping articles saves roughly 5-8% of tokens and costs every reader effort (most of all anyone reading in a second language), while the structural cuts save far more and cost nothing. **Cuts:** preamble/pleasantries, tool-call narration, restating the user's question, the same fact repeated across heading + bullet + closing line, a closing summary on a reply under ~10 lines, surveys of options that will not be recommended, decorative tables/emoji, long raw logs (quote the one decisive line), hedging. **Never cuts:** full sentences and articles, negations (not/never/only/except), numbers/units/versions/`file:line`, verbatim code, error strings and API names, and anything skipped/failed/uncertain/assumed — a shorter report never turns a partial result into a clean one. Work reports capped at three lines (what changed / what was verified / what is left), only the lines with real content. **Simple English:** the common word over the rare synonym, one idea per sentence (about 20 words or fewer), no idioms or figurative verbs, concrete names over umbrella words ("the system", "the pipeline"), technical terms kept and defined in plain words on first use, active voice. **Questions to the user:** one at a time, numbered options with a `[REC]` default (AskUserQuestion when available), so the answer can be one number — the user's words cost tokens too. **Steps back to full prose on its own** for security warnings, destructive-action confirmations, hand-followed multi-step instructions where order matters, and when the user repeats a question (the repeat means the short version did not land → answer longer and in simpler words, not shorter), resuming after. **Boundaries:** chat replies only — code, comments, commit messages, documentation, PR/issue/ticket text, memory files, and messages for other people stay at normal length. Two entry points: a **length** ask ("be brief", "too many words") switches on every rule, while a **voice-only** ask ("humanize your responses", "remove the AI tells", "your replies sound like ChatGPT") switches on the simple-English and no-AI-tells rules and leaves the length caps off (the cut list is split into *always* and *only when asked for shorter replies* for exactly this; the three-line work-report cap and one-question-per-message are length rules too) — that request is for a different voice, not for less content. The `No AI tells` section covers what simple English misses: em dashes, "not just X, but Y", forced groups of three, AI vocabulary, "serves as" for "is", puffery, bold-label lists, sycophancy, feeling-words, connector colons. The same words aimed at a file instead of at the replies ("humanize this README") are `unslop`'s, and the routing is stated in both descriptions. Persists for the session until "normal mode"/"stop clear-and-short". The plugin's `UserPromptSubmit` hook makes the voice half an **always-on default**: it emits the VOICE directive on the **first prompt of every session**, so replies are in plain voice from the start without anyone asking — the voice directive and not the length one deliberately, because this is a default and a default must not silently drop content the user never asked to lose. It emits once per session, not on every prompt (re-injecting the same text every turn adds nothing and would conflict with an explicit "normal mode" later in the session); seen sessions are recorded in `~/.claude/.clear-and-short-sessions.json`, entries older than 7 days are pruned, the file is written atomically, and a missing or corrupt file never blocks a prompt. A prompt that matches the skill's own patterns keeps today's behavior exactly — "be brief" still upgrades to the length rules, "normal mode" still turns the skill off — **and** it closes out the default for that session, so the voice directive can never fire a turn later and tell the model to drop length rules the user just asked for. The trigger description was validated by a real-registration A/B (2026-08-27, three skills registered under a scratch project's `.claude/skills/`, the installed user-level twin parked): the earlier wording under-triggered at roughly 8/16 across repeats — the model answered briefly inline without loading the skill, so nothing persisted — while precision was already 100%. The current wording front-loads the use-when clause, names "from now on keep it short" / "use fewer tokens" / "stop narrating every tool call" as phrases (bare "save tokens" was being read as a memory-save request), and adds the invoke-reason: invoke on the first such request even when that message also asks an ordinary question, because one shorter answer does not make the change persist. That scored 6/6 recall with 6/6 hard negatives still clean (README/release-notes prose → `unslop`, docs → `document-generate`, commit message / shorter function / summarize-a-file → no skill). Declares no `allowed-tools`/`disallowed-tools` (behavioral; must not restrict tools) and no `model:` pin. No `references/` (body is small). Also carries caveman's no-invented-abbreviations and no-arrows rules (the tokenizer splits `cfg`/`impl`/`→` into as many tokens as the full words, so they save nothing) and its never-add-a-word / no-mode-announcement / reply-in-the-user's-language rules. Adapted from `juliusbrussee/caveman` (MIT, © 2026 Julius Brussee) by splitting its two mechanisms apart and keeping only the structural one — its grammar-mangling and six intensity levels are dropped; roughly caveman's `lite` level plus the simple-English and question rules.
- **`unslop`** (`skills/unslop/`) — Behavioral prose editor that removes the patterns marking text as AI-written, working from a fixed list of 31 patterns in seven groups (content, language, style, communication artifacts, filler, jargon, plain speech): puffery, AI vocabulary, "not just X, but Y", forced groups of three, synonym cycling, em-dash/colon/bold overuse, bold-label lists, title-case headings, chatbot phrases, filler, hedging, abstract metaphor nouns ("substrate", "north star"), passive voice, feeling-words instead of facts. Process: scan → rewrite preserving meaning and tone → self-audit. **Scope: human-facing prose only** — docs, READMEs, posts, emails, PR descriptions — never code, comments, commit messages, or chat replies (their length, wording, *and* AI tells are `clear-and-short`'s job, including a "humanize your responses" ask; the two are complementary). Never changes meaning, facts, numbers, or established technical terms; adds no opinions or first-person voice; a project style guide overrides a conflicting pattern. Produces no files; edits the given text. Declares no `allowed-tools`/`disallowed-tools` and no `model:` pin. No `references/`. Adapted from `cursor/plugins` pstack (MIT, © 2026 Lauren Tan); upstream's "Adding soul" section (opinions, first person, deliberate mess) and its `Must always apply.` trigger are dropped — the first conflicts with the catalog's plain-facts style, the second would fire on every turn.

   - This `CLAUDE.md` — add a bullet to the **Current skills** list above.

## Distribution mechanism

Two mechanisms, with a split worth stating plainly.

Almost every skill installs with `npx skills add`, which copies one `skills/<name>/` tree into `~/.agents/skills/<name>` and symlinks that into `~/.claude/skills/<name>`. It installs skill files and nothing else, so an edit here does not reach an installed skill until the command runs again.

A skill that also needs a non-skill component — hooks, agents, MCP servers, LSP — is published as a plugin as well, through `.claude-plugin/marketplace.json`. There are two entries today, both with `"source": "./"`: `clear-and-short`, for its `UserPromptSubmit` hook, and `execute-change`, for the three hooks that watch its subagents. `hooks/README.md` covers what each hook does and how a teammate installs it.

```
claude plugin marketplace add Mi9-LLC/agent-skills
claude plugin install clear-and-short@mi9-agent-skills
claude plugin install execute-change@mi9-agent-skills
```

**Both entries declare their hooks inline**, as a `"hooks"` object mapping hook event names to matcher arrays. There are two reasons, and both matter. First, a marketplace entry rejects a hooks file path — the CLI's own error text starts `hooks: the file-path and array forms are not yet supported in a marketplace entry.` and then names the two supported forms, the plugin's own hooks file or an inline object. Second, a hooks file auto-loads from the *plugin root*, and both entries share the repo root as their plugin root, so one hooks file there would load into **both** plugins — installing `execute-change` alone would have silently registered the `clear-and-short` `UserPromptSubmit` hook as well.

The earlier Bitbucket-hosted `mi9-plugins` marketplace was retired because the Claude Code TUI's `/plugin install` flow hit a "source type not supported" bug that blocked teammates from installing through the UI. The marketplace came back on 2026-08-27 to carry the hooks, this time from GitHub. If that bug returns, move the plugins to a second repo rather than dropping the hooks.

Do not install one skill both ways on the same machine. Two copies register under the same name, and only the plugin carries the hooks.
