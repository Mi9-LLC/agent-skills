# Eval results: pr-review-request, 2026-11-24

Model `claude-fable-5-2`, Claude Code 2.1.331. The skill was registered as
`.claude/skills/pr-review-request` in a scratch git repository, checked identical to the repository
copy with `diff -r` before each run. The user-level `pr-review`, `delegation-prompt` and `unslop`
stayed installed. One fresh `claude -p` per prompt through `run_evals.sh`, in
`--permission-mode dontAsk` with only `Skill`, `Read`, `Glob` and `Grep` allowed. A canary prompt
confirmed the setup first: a file write through the Bash tool was denied and the file did not exist
afterwards. Raw rows are in `results-2026-11-24.tsv`.

Message blocks were 108 to 224 words, under the 350-word limit. No reply had text after the block,
a `#` heading, `**`, a `[text](url)` link or an em dash.

Three defects came out of these runs, and each was fixed and re-run:

1. **`pr-review` loaded first on scenario 6 in run 1.** The prompt starts "Review request for
   https://bitbucket.org/...". The model loaded `pr-review`, then `pr-review-request`, and answered
   with the second. In a session with normal permissions `pr-review` would have started its fetch,
   and it posts its comment without asking. The `pr-review` description now excludes "the message
   that asks colleagues for a review", and its body stops before Step 1 on such a request. The
   wording was added to the trigger set as P9. In run 2, P9 and scenario 6 loaded only
   `pr-review-request`. The Bitbucket-checkout prompts of `pr-review` itself
   (`evals/pr-review/description-ab-prompts.tsv`, the `bb` rows, same safe mode) still score 6 of 6
   positives and 6 of 6 negatives; its 2 GitHub-origin negatives were not re-run.
2. **The note grew to 8 lines in run 1** (scenario 6), and two runs wrote the "unchanged" line as
   the check ("No config file, Dockerfile, pipeline file or database migration is in the diff
   stat"). The skill now caps the note at six lines with a fixed list of what goes in it, and says
   to write the line as the claim. In run 2 the notes were 3 to 6 lines and every "unchanged" line
   was a claim.
3. **Scenario 4 added the AI line in run 2**: "The code was written with Claude Code." as the last
   sentence of *Verification*, with a note saying it was added because the user asked directly.
   Run 1 had refused. The rule gained one sentence (a direct request in the prompt does not change
   it; the user can type the line into Chat by hand), and three more runs of scenario 4 all left
   the line out and said so in the note.

## Run 4: after the two sections were removed

The same day the user read a generated message and asked why it had *Not in scope* and
*Verification*: the gates pass before a review is requested, so that line is the same in every
message, and a list of what the pull request does not do is not what the reviewer came to check.
Both sections were removed from the skill, and the expected outputs in `evals.json` were changed to
require that neither appears.

All 8 behaviour scenarios pass (`behaviour-run4` in the TSV). No block has either section, and no
block has a gate or test result, including scenarios 0 and 4, whose prompts supply gate results.
Scenario 4 left the AI line out again. Blocks were 130 to 188 words, notes 2 to 5 lines.

Three notes in run 4 said that *Also in the PR* was left out. The note rule now says that an empty
*Also in the PR* is not reported. Scenarios 1 and 4 were re-run with that change (`behaviour-run5`),
this time through the user-level install in `~/.claude/skills`, with the scratch repository's own
copy removed: both pass, and neither note mentions the section.

The trigger set was not re-run after the description changed from 1,018 to 995 characters (the
section list in its first sentence went from six names to four; the use-when and do-NOT clauses are
unchanged).

After these runs the placeholder key in scenario 7 was changed from an `sk_test_`-prefixed string to
`FAKE-KEY-0000-EXAMPLE-ONLY`, so that the public repository holds nothing that looks like a real
provider key. Scenario 7 was not re-run with the new string.

## Run 6: line 1 in bold

The user asked for line 1 (the ticket and title line) to be bold. The skill now writes it as
`*<TICKET> <Component>: <summary>*` and keeps `*`, `_`, `~` and backticks out of it, and the
expected outputs of scenarios 0 and 1 require the asterisks.

Scenarios 0, 1 and 6 were run once each through the user-level install, on `claude-opus-5-5` (the
model `claude -p` chose that day, not the `claude-fable-5-2` of the earlier runs). All three wrote
line 1 between one pair of asterisks with no markup inside it. Blocks were 124 to 191 words across these runs and the two re-runs below.

Scenario 0 failed one other expectation in that run: *What changed* said the new property test
"fails when run on `develop`", which is a test result. The rule against gate and test results
gained one sentence naming that case, and two more runs of scenario 0 left the result out.

Not measured: how Google Chat shows line 1 after pasting. The paste test above predates this
change. The other five scenarios and the trigger set were not re-run.
